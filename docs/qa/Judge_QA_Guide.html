Judge Q&A guide · EDU AI Engineering Hackathon 2026, Round 2 (onsite final)

Phase 1: predict the risk. Ward-level weekly dengue forecasts 2, 3 and 4 weeks ahead from rainfall, temperature and humidity lags.

Phase 2: plan the response. Turn those forecasts into supply allocation, spraying-crew deployment, hospital overflow routing, a what-if simulator and dispatch notices, all running on one laptop without internet.

How to use this guide

  • Section 1 is the 60-second summary to memorise.
  • Sections 3–10 explain each module: what it does, the exact method, why we chose it, and a worked example with real numbers from our app.
  • Section 12 lists the questions judges are most likely to ask, with short answers you can say out loud.
  • Section 13 lists honest limitations. Say these before the judges find them.

Every number in this guide was produced by the application or its tests on 27 Nov 2026. Forecasts are retrospective replays of the supplied dataset (ends 29 Dec 2025), not live surveillance.

1. 60-second summary

"Dengue cases follow rain by two to four weeks: rain creates breeding water, mosquitoes take 7–10 days to develop, the virus incubates in the mosquito and then in people. Our Phase 1 model uses exactly that delay to forecast every one of 60 wards two, three and four weeks ahead. On 2024–2025 data it never saw, its error is about one case per ward per week, roughly 40% better than assuming next week looks like this week. In Phase 2 we turn the forecast into action. The supply engine converts predicted cases into saline, kits and beds using ratios we recovered exactly from the onsite data, then shares scarce stock by risk tier and population density, never exceeding stock. Spraying crews go where the model says they prevent the most cases. Overflow patients are routed only within the same city. The simulator shows the 2–4 week effect of crews, with the efficacy clearly marked as an assumption. Every number on screen, in the SMS, the WhatsApp text and the printable brief comes from the same computation, and the whole system runs on this laptop with the internet switched off."

3. Architecture

Official XLSX → prepare_data.py → official.csv + supply.csv → common.py (validate, ward-grouped lag features) → train.py → forecaster.joblib
forecaster.joblib (loaded once) → app.py (FastAPI, cached forecasts) → operations.py (pure maths) → phase2.py (plan, simulate, dispatch, brief, exports) + community.py (map data, facilities, reports) → React build served by the same process on 127.0.0.1:8000
  • One computation, many outputs. /api/plan computes demand, allocation, crews and overflow once. The screen, SMS, WhatsApp text, printable brief and CSV all read that same result, so they can never disagree.
  • All maths in the backend, deterministic. Same inputs always give the same output (a test checks this). The browser only displays.
  • No database server. The dataset is 2.6 MB; pandas in memory is faster and has fewer offline failure points than MySQL. Citizen reports use SQLite from the Python standard library.
  • Caching. Model loads once at startup; forecasts cached per (week, horizon); plan cached per input set; GET responses carry a 5-minute cache header; hashed build files cache forever, pages revalidate.
  • Startup safety. The app refuses to start if the CSV's SHA-256 does not match the fingerprint stored in the model, so a wrong dataset cannot silently produce wrong forecasts.

Leakage point to mention: the three supply columns are computed from actual cases in the same week, so using them as model inputs would leak the answer. We never feed them to the model. We only used them to recover the per-case ratios, then apply those ratios to predicted cases.

How we found the ratios

We searched ratios r and rounding rules so that rule(r × cases) equals the column for all 31,320 rows. Round-half-up fits all three. Every ratio inside these intervals reproduces 100% of rows, and we use the mid-points: saline 2.3834–2.3863 → 2.385, kits 1.1618–1.1666 → 1.164, beds 0.2970–0.2995 → 0.298. A test re-checks all rows every run.

5. Forecasting model (Phase 1, unchanged)

Features (all computed per ward, only from weeks ≤ the issue week)

  • Rainfall this week and 1–4 weeks before; 4- and 8-week rain totals
  • Temperature and humidity now and 4-week mean
  • Reported cases now and 1–3 weeks before, 4-week mean
  • Ward traits: population density, waterlogging risk index, sanitation score
  • Season: week-of-year as sine and cosine (so week 52 sits next to week 1)

Why lags of 2–4 weeks: rain creates standing water → Aedes egg to adult takes 7–10 days (CDC) → the virus incubates 8–12 days in the mosquito (WHO) → symptoms start 4–10 days after infection (WHO). So this week's rain shows up in reported cases roughly 2–4 weeks later. That is why the horizons are 2, 3 and 4 weeks.

Why HistGradientBoosting with Poisson loss

  • Cases are non-negative counts with monsoon spikes. Poisson loss models counts directly and never predicts negative cases.
  • Rain × season × ward interactions are non-linear (rain in January matters less than rain in July). Trees capture this; Ridge cannot.
  • Fast on 30k rows, handles missing values natively, no scaling needed. Ridge kept as a transparent comparator.

Rain dominates at 2–3 weeks, season at 4 weeks. Recent cases matter very little — which is why our simulator does not work by "lowering recent cases" (see section 9).

Risk tiers

Cut-offs are the 50th, 80th and 95th percentiles of weekly ward cases in the training period only (0, 5, 13). Observed counts are integers, so a continuous prediction is compared at 0.5, 5.5 and 13.5 (continuity correction); a test proves every integer gets the same tier as an observed count would. Tiers are relative burden, not per-capita rates (the data has no ward populations).

Leakage protections (each has a test)

  • Lags match manual per-ward slices, so no value crosses a ward boundary.
  • Scrambling every observation after week t leaves all features at week t unchanged.
  • Train, validation and test masks never overlap; split uses both issue and target dates.
  • Tier cut-offs and uncertainty bands are fitted before the test set is touched.

6. Resource allocation engine

Demand per ward = round_half_up(predicted cases × ratio) for saline, kits and beds.
Available stock = slider % × total demand in scope (the dataset has no stock levels; officers can set each resource separately).
Priority = tier weight (Low 1, Medium 2, High 3, Critical 4) × (0.75 + 0.25 × density percentile). Any High ward (≥ 2.25) always outranks any Medium ward (≤ 2.0); within a tier, denser wards come first.

Algorithm

  1. Fairness floor: every ward first gets 25% of its demand (adjustable 0–100%). If even the floors don't fit, they are shared proportionally (largest-remainder method, exact integers).
  2. Priority fill: remaining units go to wards in priority order until each ward's demand is met or stock runs out.

Why this is defensible: step 2 is the exact optimum of "maximise Σ priority × units delivered" subject to stock, demand caps and floors (a fractional knapsack with unit weights has an integral greedy optimum). Our tests compare it with an LP solver (SciPy HiGHS) on 15 random cases — identical objective every time. Guarantees, all tested: integers, 0 ≤ allocation ≤ demand, Σ allocation = min(stock, demand), floors respected, deterministic.

Deficit alerts: a ward is flagged when any resource is below 100%; critical if it gets under 50% or is High/Critical tier.

Worked example (issue week 4 Aug 2025, 2-week horizon, all cities, stock 50%): saline demand 969, stock 485, allocated 485, deficit 484; kits 469 / 235 / 235 / 234; beds 120 / 60 / 60 / 60. 43 wards flagged. Top priority ward: DSCC Ward 04 (High tier, highest density).

7. Spraying crews and larvicide

  • Larvicide limit: deployable crews = floor(total crews × larvicide supply %). One supply set per crew is an assumption. Example: 10 crews at 70% → 7 deploy, 3 idle.
  • Assignment: each next crew goes to the ward where it prevents the most predicted cases (ties → higher priority). Because each ward's response is concave (each extra crew adds less), this greedy is the exact optimum for the crew budget; a test checks it against brute force over all combinations.
  • Maximum crews per ward (default 3) prevents piling every crew into one ward. Crews are never double-counted (Σ ≤ deployable).
  • The plan flags High/Critical wards that got no crew.

8. Hospital overflow routing

Bed demand per ward = round_half_up(0.298 × predicted cases). Capacity is not in the dataset, so the default is each ward's 90th-percentile weekly bed requirement in 2016–2022 (minimum 1), times a capacity-scale slider. This is labelled as an assumption everywhere.

Routing (per city only): patients treated locally = min(demand, capacity); excess = demand − capacity. Each excess patient goes, one at a time, to the ward in the same city whose utilisation after receiving them would be lowest (water-filling). This levels load, moves the maximum possible number (min(total excess, total headroom)), and never counts a bed twice. Whatever cannot be placed is reported as unmet.

Worked example (issue week 30 Jun 2025, 2-week horizon, default capacity): Chattogram CCC Ward 07 → Ward 04: 1 patient; Dhaka North DNCC Ward 12 → Ward 16: 1; Dhaka South DSCC Ward 04 → Ward 03: 1. No unmet demand. With capacity scale 0.85 and 4 Aug 2025, 3-week horizon: 7 patients routed across 4 cities, 3 unmet.

City-wide utilisation does not change with routing (the patients stay in the city); ward-level utilisation does. Routing is a planning recommendation, not a transfer order: there are no hospital names, distances or travel times in the data.

9. Vector-control simulator

Baseline = the ML forecast for weeks 2, 3 and 4 for each ward.
Scenario = baseline × (1 − reduction(k) × onset(h)), with reduction(k) = min(cap, 1 − (1 − p)k) for k crews, p = assumed transmission cut per crew (default 10%), cap default 50%; onset = 50% / 85% / 100% at 2 / 3 / 4 weeks.
Outputs: cases prevented per horizon, bed and saline savings (via the same ratios), ROI = cases prevented (weeks 2–4) ÷ crews; zero crews → ROI not defined (shown as —, never ∞).

Why not feed reduced inputs into the ML model?

We tested it. Lowering the recent-case features changed city totals by under 1% (the model barely uses them). Lowering rain features gave non-monotone results in up to a third of steps (tree models extrapolate in steps). A forecasting model learns correlations, not the causal effect of spraying. So we keep the ML model as the baseline and apply an explicit, adjustable effect — which a judge can inspect and change on screen.

Why the onset shape: spraying works on mosquitoes now; infections already incubating still appear. Using CDC/WHO timings (egg→adult 7–10 days, mosquito incubation 8–12 days, human 4–10 days), averted infections show up mainly 2–4 weeks later.

Worked example (4 Aug 2025, 12 crews, defaults): baseline 407.1 / 528.4 / 497.4 cases at weeks 2 / 3 / 4 → 401.0 / 515.8 / 483.8. Prevented 6.14 + 12.66 + 13.59 = 32.38 cases; beds 159 → 153 at week 3; saline 1,263 → 1,233. ROI 2.70 cases per crew. Best wards: DSCC Ward 04 (2.87), CCC Ward 01 (2.81), DNCC Ward 12 (2.79).
Say clearly: "The efficacy is an assumption, not a measured effect. The dataset has no intervention records, so no one can measure it from this data. We expose it as a slider so planners can test pessimistic and optimistic cases. The ranking — which wards benefit most — depends mainly on the forecast, so it is fairly robust to the exact efficacy value."

10. Dispatch notices and briefs

  • SMS (English, ≤160 characters; measured maximum 152 over a range of scenarios) and Bangla SMS (with segment count): ward, issue date, target week, predicted cases, tier, allocated/required saline, kits, beds, crews, deficits.
  • WhatsApp (English and Bangla): the same plus the 80% range, priority rank and a "planning guidance, not a clinical order" note.
  • Commissioner brief: printable HTML with print stylesheet (Print / Save as PDF): supplies, alerts, ward allocation in priority order, overflow and transfers, simulation and ROI table, all assumptions.
  • CSV exports: allocation, overflow, simulation, all messages.
  • Nothing is sent. Templates are copied into an approved gateway. Copy buttons work offline.

11. Map Hub, facilities and citizen reports

  • Map: real district outlines (geoBoundaries, Bangladesh Bureau of Statistics / OCHA, CC BY 3.0 IGO) and real city-corporation centres; the team's WardMap tiles show every ward's tier and predicted cases. Ward boundaries do not exist in the data, so wards are a schematic grid and labelled as such.
  • Layers: district borders, supply shortage, spraying crews, bed transfers, nearby healthcare — each says who it is for.
  • Nearby healthcare: 2,420 hospitals, clinics and pharmacies within 7 km of each city centre from OpenStreetMap (ODbL), saved locally. Phone shown only where OSM has one (127 do). No capacity data. Map links hidden when offline.
  • Citizen reports: standing water, open garbage, broken sewer; ward; optional GPS and photo. No name or phone collected. Photo is re-encoded in the browser (removes GPS metadata), then checked on the server by its actual bytes (only JPEG/PNG, ≤1.5 MB), stored under a random file name. Duplicate taps are stored once (client request ID). Submit button disables when the service can't be reached. Officers can mark reports reviewed or resolved.
  • Hotlines: 999 (National Emergency Service, listed on bangladesh.gov.bd) and 16263 (Shastho Batayon, listed on 16263.dghs.gov.bd and dghs.gov.bd), pinned at the bottom of every page with tap-to-call.

12. Likely judge questions and answers

Q1. Why 2, 3 and 4 weeks?

Rain → breeding (7–10 days) → mosquito incubation (8–12 days) → human symptoms (4–10 days) puts the rain-to-case delay at about 2–4 weeks. Shorter is too late to act; longer loses accuracy (MAE rises from 1.04 to 1.28 already).

Q2. How do you know there is no data leakage?

Features use only weeks ≤ issue week within the same ward (tested by scrambling the future); split is by target date so training targets never enter validation; thresholds and bands are fitted before the test set; the three supply columns, which come from actual cases, are never model inputs.

Q3. Why Poisson loss?

Target is a count. Poisson loss fits the log of the expected count, so predictions are always ≥ 0 and the variance grows with the mean, as it does in outbreak weeks. Squared error over-weights rare spikes.

Q4. MAE 1.04 — is that good?

It is about one case per ward per week on 2024–25 data the model never saw. The naive "same as last week" baseline is 1.69, so we are about 39% better; the ward-average baseline is 3.10. RMSE 2.09 is higher because big outbreak weeks are harder.

Q5. Why not deep learning / LSTM?

30k rows, tabular, need for explanation and offline CPU inference. Gradient boosting is the standard strong choice here; it trains in seconds and we can show which feature groups drive it.

Q6. How were the risk thresholds chosen?

Training-period percentiles (50th, 80th, 95th) of weekly ward cases: 0, 5, 13. Data-driven, fixed before testing, and the same for every ward so tiers are comparable.

Q7. Where do saline/kit/bed numbers come from? Did you invent them?

No. The onsite file contains them, and they are exact functions of cases. We recovered the ratios (2.385, 1.164, 0.298, round half up) and a test confirms they reproduce all 31,320 rows. We apply them to predicted cases.

Q8. Is the allocation optimal?

For the stated objective — maximise priority-weighted units delivered, after a fairness floor, within stock and demand — yes: it is a fractional knapsack with unit weights, and our tests match an LP solver exactly. We don't claim it is optimal for health outcomes, which the data cannot measure.

Q9. Why not give everything to the highest-risk wards?

That starves lower-tier wards completely. The 25% floor (adjustable, can be set to 0) keeps a minimum service everywhere; the rest follows risk. Officers can see the effect live.

Q10. Why does density matter?

Aedes transmission spreads faster where people live close together. But density only orders wards inside the same risk tier; it can never push a Medium ward above a High one.

Q11. Can allocation ever exceed stock?

No. Σ allocation = min(stock, demand), each ward ≤ its demand, integers only. Tests check this at 30, 45, 70, 99 and 100% stock and on random cases.

Q12. Where does bed capacity come from?

The data has none. We use each ward's 2016–22 90th-percentile weekly bed need as a placeholder, clearly labelled, with a slider. It must be replaced with real hospital capacity before real use.

Q13. Why only within the same city?

The brief requires it, and city corporations run their own health services. Our code builds a separate pool per city; a test asserts every transfer has the same city at both ends.

Q14. How do you avoid double-counting beds?

Local patients fill local beds first; each transferred patient is placed only into a bed still free after local patients and earlier transfers; total moved = min(total excess, total headroom). Tests check conservation (out = in) and that no ward exceeds capacity.

Q15. The simulator — is "cases prevented" real?

It is a scenario estimate. The forecast is real model output; the spraying effect is an assumption shown on screen and changeable. We tested putting reduced inputs into the model and it was not reliable, so we did not pretend it was causal.

Q16. What does ROI mean here?

Estimated cases prevented over weeks 2–4 divided by crews sent to that ward. Example: 12 crews → 32.4 cases prevented → 2.70 per crew. Zero crews → not defined, never divided by zero.

Q17. Why does each extra crew help less?

Reduction = 1 − (1 − p)k: the second crew works on the mosquitoes the first one missed. This concave shape also makes greedy crew assignment provably optimal.

Q18. What happens offline?

Everything core: forecasts, allocation, routing, simulation, dispatch, maps, facility list, fonts, photo. Only citizen report submission requires the service; it disables with a message. Our browser test blocks all non-local traffic and passes 13 checks; start.cmd downloads nothing.

Q19. Do you use ChatGPT / an LLM at runtime?

No. No LLM, no paid API, no external call for any calculation. AI (Claude Code) was used to help write code and docs; it is disclosed in the README.

Q20. Is the map real?

District borders and city centres are real (geoBoundaries / BBS). Ward boundaries are not in the data, so we show wards as a labelled grid instead of inventing shapes.

Q21. Are the facility phone numbers real?

They come from OpenStreetMap volunteers, shown only where recorded (127 of 2,420), labelled unverified. We invented none.

Q22. How are uploaded photos made safe?

Browser re-encodes the image (strips GPS/EXIF); server checks the real file signature (JPEG/PNG only, ≤1.5 MB), ignores the claimed type and filename, saves under a random ID, serves with nosniff; path traversal is blocked (tested). No personal data is collected.

Q23. Who can see reports?

In this demo there is no login, so the officer list is open — this must get authentication before real use. We say this on screen.

Q24. Are these live 2026 forecasts?

No. Data ends 29 Dec 2025. Every screen says forecasts are retrospective replays and marks whether a week was in the training period or the held-out test period.

Q25. How do you know the system works on another computer?

setup.cmd builds everything from the workbook and runs the tests; retraining reproduces a byte-identical model (same SHA-256), and the app refuses to start if the dataset fingerprint differs.

Q26. Why should the SMS and the brief match the screen?

They are not separate calculations: all are rendered from the same cached plan result for the same inputs. A test checks that a ward's SMS numbers equal its allocation.

Q27. Why Bangla first?

The audience is ward commissioners, health workers and citizens in Bangladesh. Bangla is default; English is one tap and keeps all selections. All dictionaries are local.

Q28. What would you do with more time?

Real hospital capacity and stock feeds; field-measured spraying efficacy to calibrate the simulator; verified ward boundaries; login and roles for report review; real user testing with low-literacy citizens.
